# Подготовка политики: распределение ответственности

Это техническая карта для завершения политики, не утверждённая юридическая редакция.

## Разработчик — подготовлено

- В форме: имя, предприятие, телефон/email, регион, тип обращения, комментарий, состав заявки (исполнение, размеры, толщина, длина, объём), до 5 вложений общим размером до 15 МБ и согласие.
- Черновик и выбранные позиции — sessionStorage вкладки браузера. После подтверждённой отправки черновик очищается; согласие автоматически не восстанавливается. При ошибке данные остаются для повторной попытки.
- Будущий маршрут: браузер → HTTPS/Nginx → собственный SMTP API → почтовый сервер → заданный ящик организации. Заявки в базу каталога не записываются; API не сохраняет тексты обращений на диск и не пишет их в логи.
- SMTP API временно держит данные и вложения в памяти во время отправки. Вложения проверяются по расширению и сигнатурам PDF/JPG/PNG и отправляются письмом; они не сохраняются на диск сайта. Для ограничения частоты и повторов используются хеши IP и содержимого до 10 минут; они не записываются на диск. Очистка просроченных записей происходит при следующем запросе или завершении процесса.
- Логи Nginx для endpoint заявки отключены. Логи остальных страниц могут содержать IP и сведения запроса; срок их хранения зависит от настроек сервера. Почтовый провайдер и оператор могут сохранять письма и служебные журналы.
- SMTP проверен в локальной конфигурации. Постоянный хостинг и внешнее размещение ещё не выбраны; страница /privacy/ остаётся предварительной и требует утверждения оператором.

## Заказчик подтверждает

- Кто из сотрудников получает обращения и имеет доступ к ящику.
- Сроки хранения обращений и основание выбранного срока, порядок удаления писем и копий.
- Контакт и порядок обработки просьб об удалении/отзыве согласия.
- Выбор провайдеров, размещение данных и договорённости с ними — совместно с разработчиком при подключении.

## После подтверждения — разработчик

Внести конкретные сроки, провайдеров и порядок обработки в политику; согласовать итоговую редакцию с оператором; настроить хранение журналов, проверить очистку и форму согласия. Не считать политику завершённой только по наличию текста и реквизитов.

Характеристики продукции, география, адрес посещения, разрешения на фото/документы также требуют ответа заказчика. Вопросы уже собраны в CUSTOMER_CHECKLIST.md; дублировать запрос не требуется.

## Учётные записи сотрудников

Приватный JSON на сервере содержит логин, отображаемое имя, роль, статус доступа, scrypt-хеш пароля и историю изменений с именем редактора (до 20 версий карточки). Email для входа не нужен. Сессии: сервер хранит хеш токена, CSRF-токен, ID/версию аккаунта и срок; браузер — HttpOnly/SameSite=Strict cookie до 7 дней, Secure при HTTPS. Выход/сброс/отзыв доступа аннулируют сессии. Просроченные сессии очищаются при следующем входе; неактивные аккаунты остаются до отдельного удаления ответственным.

Каталог содержит черновики и опубликованные сведения; посетителям доступны только публикации. Фото/PDF отдельно на том же сервере; с изображений удаляются метаданные при преобразовании. История, откреплённые файлы, 30 снимков JSON и 14 полных резервных копий требуют согласованного порядка удаления. Backup не содержит действующих сессий. Удаление файлов из карточки не является полным удалением из хранилища или копий.

Оператору нужно определить сотрудников/роли, сроки хранения их учётных записей, истории и резервных копий, порядок отключения и удаления доступа. Это часть окончательной политики перед публикацией. Реальный хостинг и перенос резервных копий за пределы сервера ещё не настроены.
