# Подключение почты и каталога

## Готово и что ещё требуется

Код отправки, миграции, права редакторов и редактор подготовлены. Реальный SMTP и Supabase не подключены: нет параметров выбранных сервисов. Docker в текущем окружении отсутствует. Тесты SMTP используют локальный приёмник; тесты базы используют PostgreSQL/PGlite. Это не проверка доставки в настоящий ящик и не проверка Supabase Auth.

## SMTP

1. Скопировать `.env.server.example` в `.env.server` в корне. Заполнить `SMTP_HOST`, `SMTP_PORT` (465 или 587), `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`, `MAIL_TO`. Последние два могут совпадать. Использовать отдельный пароль приложения, если его поддерживает почтовый сервис. `SITE_ORIGIN` — точный origin сайта, без завершающего `/`.
2. Секреты не добавлять в `NEXT_PUBLIC_*`, Git и статическую сборку. Сертификат SMTP проверяется; TLS обязателен. Для проверки конфигурации можно запустить `npm run start:api`. Без SMTP запросы получают 503, успешная отправка не имитируется.
3. Для выпуска: настроить `deploy/.env` с SITE_DOMAIN и STATIC_ROOT; сертификаты и статический релиз подготовить по существующему Nginx-конфигу. Из deploy запустить `docker compose --env-file .env --env-file ../.env.server up -d --build`. API доступен только во внутренней сети Compose. DATABASE_URL не передаётся в почтовый контейнер. Конфигурация контейнера подготовлена, Docker-сборка здесь не выполнялась.
4. В окружении сборки сайта установить `NEXT_PUBLIC_FORM_ENDPOINT=/api/request`, затем `npm run build`. Перед включением согласовать обработку данных. Для отката отключить endpoint и пересобрать статический сайт.
5. После подключения отправить согласованную тестовую заявку и проверить её получение, включая папку спама, кодировку, состав, исполнение, длину и контакт. Сам факт принятия письма SMTP-сервером ещё не доказывает попадание во входящие.

Ограничения: не больше 5 попыток за 10 минут с одного IP, тело до 64 KiB, фиксированный получатель, проверка Origin и согласия, honeypot. Прокси заменяет X-Real-IP, прямой доступ к API запрещён. Один API-процесс; ограничения и отпечатки повторов хранятся в памяти 10 минут, сбрасываются при рестарте. После ошибки SMTP автоматического повтора нет; при обрыве после принятия письма повторная ручная отправка может дать дубль. Очереди писем и гарантии exactly-once нет.

## База каталога и редакторы

1. Выбрать Supabase-проект и регион размещения. В `.env.server` задать административный `DATABASE_URL` (прямое подключение или session pooler). Для удалённой базы используется TLS с проверкой сертификата. При собственной CA задать `NODE_EXTRA_CA_CERTS`, не отключать проверку.
2. Запустить `npm run db:migrate`: все миграции применяются в транзакции, с блокировкой, журналом и контрольными суммами. Повтор не дублирует миграции; изменение уже применённого файла останавливает запуск. Если миграции ранее выполнялись вручную, сделайте резервную копию перед первым запуском: их идемпотентные версии будут выполнены ещё раз и зарегистрированы в журнале.
3. `npm run db:check` проверяет доступность таблиц, количество позиций/редакторов и включение RLS, не печатая содержимое базы и секреты.
4. Отключить самостоятельную регистрацию в Supabase Auth. Создать/пригласить только подтверждённых заказчиком сотрудников через панель Supabase. Письма-приглашения отправляются только при согласованном подключении. Пользователь подтверждает email.
5. Указать `EDITOR_EMAIL` в `.env.server`, выполнить `npm run db:editor -- grant`. Команда выдаёт доступ только существующему пользователю с подтверждённым email и перечитывает результат. `npm run db:editor -- revoke` отзывает права; ограничения RLS действуют и для уже выданной сессии.
6. Настроить Auth Site URL и Redirect URL `<origin>/admin/`. Для приглашений/magic links отдельно настроить доставку писем Supabase Auth: SMTP API заявок не отправляет письма входа.
7. Указать публичные `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` при сборке. Service-role и DATABASE_URL в браузер не передаются. Пересобрать сайт.
8. Приёмка: разрешённый сотрудник входит по ссылке, сохраняет позицию, изменение видно в каталоге после обновления; посторонний пользователь не может писать; после revoke действующая сессия теряет право записи. Сверить характеристики и документы, проверить выход и ошибку сети.

До реального подключения нет учётных записей сотрудников и не подтверждена доставка magic links. Команды подготовки не создают внешний проект и не отправляют приглашения автоматически.

## Основания технической реализации

- Nodemailer SMTP/TLS: https://nodemailer.com/smtp
- Supabase email sign-in и запрет автоматической регистрации: https://supabase.com/docs/guides/auth/auth-email-passwordless
- PostgreSQL TLS: https://node-postgres.com/features/ssl
