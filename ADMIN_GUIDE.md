# Управление каталогом

## Для сотрудника

1. Нажмите «Вход» в шапке сайта (на телефоне — в меню). Введите выданные логин и пароль. Регистрации и подтверждения по почте нет.
2. Выберите товар/услугу или нажмите «Добавить». Поиск и фильтр помогают найти нужную позицию.
3. Укажите тип, название, описание. Остальное необязательно: подробности, фотографии, характеристики, документы, поля выбора для клиента.
4. «Сохранить черновик» сохраняет работу, не меняя сайт. «Предпросмотр» показывает карточку. «Опубликовать» сразу обновляет публичный каталог без пересборки сайта.
5. «Скрыть с сайта» убирает позицию для посетителей. Её можно вернуть. «Создать копию» создаёт отдельный черновик. «История» возвращает прежние данные в черновик; затем требуется публикация.

Фотографии: до трёх JPEG/PNG/WebP, каждая до 10 МБ; первое фото главное, порядок можно менять. Сервер уменьшает изображение до 2000 px и преобразует в WebP. Указывайте короткое описание фото. Без фотографий карточка остаётся текстовой. PDF: до 10 файлов на карточку, каждый до 10 МБ. Загружайте только разрешённые материалы.

Характеристики — пары «Название / Значение», например «Материал / Сталь». Поля «Что выбирает клиент» — список, число или текст; можно задать единицы, подсказку, обязательность, числовые границы. Они попадают в состав заявки. Для обычной услуги их можно не добавлять.

Если карточку успел изменить другой сотрудник, ваша форма не пропадает: скопируйте свой вариант и загрузите актуальный. При сбое сети сначала проверьте актуальную карточку — сервер мог успеть сохранить данные. При закрытии несохранённой формы появляется предупреждение.

Редактор управляет каталогом. Владелец дополнительно видит раздел «Доступы»: меняет роль и отключает/возвращает доступ; действующие сеансы сотрудника завершаются. Собственные права из интерфейса не меняются. Забытый пароль сбрасывает технический ответственный.

## Для технического ответственного

Нужен Node.js 24+ и один серверный процесс API. Хранилище рассчитано на небольшой каталог на одном сервере, на локальном постоянном диске; распределённая запись/NFS не поддерживаются. JSON и загрузки находятся вне `out/` и Git. `content/catalog.json` — только первоначальное наполнение; повторный запуск существующий каталог не перезаписывает.

Локальный запуск в двух терминалах:

```sh
cp .env.server.example .env.server
npm run start:api
```

```sh
npm run dev -- --hostname localhost --port 3000
```

Адрес — http://localhost:3000/admin/. `SITE_ORIGIN` должен точно совпадать с адресом браузера. Next dev проксирует `/api/` и `/media/` на порт 3101. В production это делает Nginx; статическому каталогу теперь нужен запущенный API.

Создание заранее согласованных учётных записей:

```sh
npm run admin:user -- create owner owner
npm run admin:user -- create editor1 editor
npm run admin:user -- list
npm run admin:user -- reset editor1
npm run admin:user -- disable editor1
```

Команда генерирует случайный пароль и сохраняет его в `.local/credentials/LOGIN.txt` с правами 0600. В терминал выводится только путь. Передайте пароль сотруднику защищённым способом, перенесите в менеджер паролей и удалите файл. Для production `CREDENTIAL_DIR` должен быть приватным записываемым каталогом. Отображаемое имя можно задать через `ADMIN_NAME`. Пароли не передавайте аргументами командной строки. Сброс завершает все сеансы; последний владелец не отключается.

В JSON хранятся scrypt-хеши паролей, хеши токенов сессий и права. Cookie HttpOnly/SameSite=Strict, при HTTPS Secure; сессия живёт до 7 дней. Каждое изменение проверяет сессию, Origin и CSRF. Ограничения входа и загрузки действуют на одном процессе. Сервис почты для авторизации не нужен.

## Данные и резервирование

- `DATA_DIR/state.json`: пользователи, сессии, медиа, черновики, публикации, последние 20 версий карточки.
- `DATA_DIR/uploads/`: загруженные файлы. Неопубликованные/скрытые файлы выдаются только сотрудникам, если они не используются другой опубликованной карточкой.
- `DATA_DIR/snapshots/`: последние 30 снимков JSON перед изменениями. Файлы не удаляются при откреплении, чтобы история продолжала работать. Лимит всего хранилища: 1000 файлов / 1 ГиБ; при достижении требуется обслуживание с учётом истории и резервных копий.
- `BACKUP_DIR`: копия JSON и всех файлов с SHA-256-манифестом; на старте API и каждые 24 часа, сохраняются последние 14 копий. Сессии в резервную копию не входят.

```sh
npm run admin:backup
npm run admin:backup -- restore /absolute/path/to/anteh-backup --confirm
```

Восстановление проверяет контрольные суммы и завершает все сеансы. Команда работает и на новом сервере, и при повреждении текущего JSON; прежний файл сохраняется снимком перед заменой. Перед восстановлением в production остановите API, чтобы никто не публиковал новые изменения в процессе. Снимок перед восстановлением сохраняется. Резервные копии защищать как основные данные; локальные снимки не спасают от потери сервера. Настроить отдельный диск и вынос копий за пределы сервера, затем проверить восстановление на запасной машине.

## Production

`deploy/compose.yaml` монтирует `DATA_ROOT` в `/data`, `BACKUP_ROOT` в `/backups`; смена статического релиза эти директории не затрагивает. До запуска создайте обе директории с владельцем UID/GID 1000 и правами 0700, настройте HTTPS и переменные `deploy/.env.example`. API наружу не публикуется, доверяет только Nginx, который заменяет X-Real-IP.

Создать сотрудника в работающем контейнере: `docker compose exec api node scripts/admin-user.mjs create owner owner`. Пароль окажется в приватном `/data/credentials/owner.txt`. Копирование и удаление файла выполняет ответственный на сервере. Для восстановления используйте `docker compose run --rm api node scripts/admin-backup.mjs restore /backups/ИМЯ --confirm` при остановленном API.

Docker и внешний production здесь не запускались: окружение требует отдельной проверки на выбранном сервере. Реальный SMTP также подключается отдельно; это не блокирует админку.
